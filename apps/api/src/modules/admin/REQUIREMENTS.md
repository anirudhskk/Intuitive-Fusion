## In scope

### FR-0680 · Must
The platform shall provide a dedicated administrative configuration interface, segmented by function: Finance (budget caps, ECV/tax settings, ERP connection settings), Users (accounts, roles, hierarchy), Legal (clause library, legal-system integration settings), Procurement (taxonomies, templates, workflow rules), Delegations (delegation-of-authority thresholds and mappings), and Other (notification channels, alert thresholds, general platform settings).

**Acceptance:** Given an administrator, when they open the configuration interface, then the six functional segments are presented and each named setting group is manageable within its segment.

### FR-0685 · Must
Access to each administrative configuration segment shall be independently permissioned, so that, for example, a Finance administrator does not require or receive access to Legal configuration.

**Acceptance:** Given an administrator permissioned for Finance configuration only, when they open the configuration interface, then Legal, Procurement and Delegations segments are not accessible and the attempt to reach them is logged.

> ⚠ Open client query — see register Notes column.

### FR-0690 · Must
Changes made within the administrative configuration interface shall be captured in the platform's audit trail, recording the administrator, the setting changed, and the prior and new values.

**Acceptance:** Given any configuration change, when the audit trail is inspected, then the administrator identity, setting name, prior value, new value and timestamp are recorded.

### FR-0695 · Must
The system shall auto-generate sequential procurement numbers in a format configurable by the customer, with the procurement number defaulting to the contract number unless the customer configures otherwise, and shall support variation numbering linked to the parent (e.g. ABC001.v1, or a financial-year scheme).

**Acceptance:** Given a configured numbering format, when a procurement is created, then the next sequential number is issued in that format; and a variation is numbered so that its relationship to the parent record is explicit.

> ⚠ Open client query — see register Notes column.

### FR-0705 · Must
The platform shall provide a library of end-to-end workflows (e.g. simple, intermediate, complex, and a high-risk/high-value workflow with added governance such as board endorsement or external probity), each with category sub-workflows (e.g. IT, events, consultants, contractors, legal, finance, risk and compliance, property, manufacturing) that produce different document outputs for the same process shape.

**Acceptance:** Given a simple workflow selected for a venue hire and for a contractor engagement, when each proceeds, then the process steps are the same but the generated procurement plan, tender and report outputs differ per sub-workflow, consistently and repeatably.

> ⚠ Open client query — see register Notes column.

### FR-0710 · Must
The platform shall offer two workflow design modes: a configurable out-of-the-box workflow set in which predefined fields can be included or excluded and administrators can define additional custom fields (e.g. an Indigenous procurement flag or tag), and a fully configurable drag-and-drop designer controlling field placement and size and the layout of the generated Word, Excel or PowerPoint output.

**Acceptance:** Given the out-of-the-box mode, when an administrator excludes predefined fields and adds a custom tag field, then the workflow reflects both changes without a code release; and in drag-and-drop mode, the designed layout governs the generated document.

> ⚠ Open client query — see register Notes column.

### FR-0730 · Should
Users shall be able to add or remove workflow steps for a specific procurement where the delegate has approved that variation to the standard process.

**Acceptance:** Given delegate approval to vary the process, when a user adds or removes a step for that procurement, then the change applies to that procurement only and the approval basis is recorded.
